## 7. Findings

### P1. Проверка токенов должна fail-closed при недоступном источнике качества

Файл: `src/v2/lib/assetQualityGate.ts:28-53`  
Файл: `src/v2/lib/assetQualitySource.ts:40-52`

Сейчас если источник не подключен, `evaluateAssetQuality` возвращает `warn`, а не `block`. Если CoinMarketCap Top-100 недоступен, неизвестный токен тоже может стать предупреждением, а не запретом.

Почему это опасно:

- логика проекта требует запрет монет вне Top-100 и Binance Monitoring;
- если внешний источник сломался, система не должна становиться мягче;
- для риск-системы правильнее: "не могу проверить качество -> не разрешаю покупку".

Ожидаемое поведение:

- при покупке нового криптоактива и недоступном источнике качества: `БЛОКИРОВКА`;
- разрешать только уже известные активы из надежного источника;
- явно писать: `Источник проверки недоступен — покупка запрещена до восстановления проверки`.

### P1. Реализованный PnL в отчетах местами считается приблизительно

Файл: `src/v2/components/V2ReportsPage.tsx:102-105`  
Файл: `src/v2/components/V2ReportsPage.tsx:206-212`  
Файл: `src/v2/components/V2ReportsPage.tsx:386-439`

В коде есть расчет:

`реализованный PnL = (цена продажи - текущая средняя входа) * количество`

Проблема:

- текущая средняя входа может не совпадать с исторической средней на момент продажи;
- после новых покупок старые продажи могут показывать неверный realized PnL;
- это противоречит учетному правилу проекта: SELL не должен пересчитываться через текущую среднюю.

Ожидаемое поведение:

- realized PnL должен приходить из accounting layer / Google Sheets;
- если точного realized PnL нет, UI должен показывать `—` или явно `оценка`, но не как основной финансовый факт.

### P2. `/api/asset-quality` локально возвращает JavaScript, а не JSON

Файл: `api/asset-quality.js:1-61`

Проверка:

`curl http://localhost:5173/api/asset-quality`

Факт:

- HTTP 200;
- `Content-Type: text/javascript`;
- тело ответа - исходный JS-код файла.

Почему это плохо:

- локально нельзя надежно проверить этот endpoint как API;
- QA может получить ложный PASS по статусу 200;
- автоматическая проверка Monitoring List должна возвращать JSON или явную ошибку, а не код.

Ожидаемое поведение:

- локально endpoint должен проксироваться через dev server или отдельный serverless runner;
- если локально endpoint не поддерживается, тест должен получать 404/501, а не JS-файл.

### P2. API health и UI health расходятся

Файл: `src/v2/lib/v2LabData.ts:305-314`

Факт:

- `/api/investor.overview.health = 0`;
- UI показывает здоровье портфеля 77-78;
- фронтенд сознательно использует собственный расчет `computePortfolioHealth`.

Это может быть допустимо архитектурно, но сейчас контракт двусмысленный:

- какой health является официальным?
- почему API отдает `0`, если UI показывает реальный показатель?
- должны ли будущие интеграции читать health из API или рассчитывать сами?

Ожидаемое решение:

- либо удалить/переименовать stale `overview.health`;
- либо привести API health к той же модели;
- либо явно задокументировать: `overview.health` legacy, не использовать.

### P2. Ручной ввод после сигнала может сбить контекст

Файл: `src/v2/components/V2GatePage.tsx:97-118`  
Файл: `src/v2/components/V2GatePage.tsx:291-296`

При переходе из сигнала есть кнопка `Ручной ввод`. После нажатия пользователь может ожидать пустую форму нового актива, но состояние формы может вернуться к первому активу из портфеля.

Риск:

- пользователь думает, что проверяет новый тикер;
- система фактически проверяет уже выбранный актив;
- это UX-риск, не финансовый баг, но для pre-trade gate он важен.

Ожидаемое поведение:

- `Ручной ввод` должен явно переводить форму в режим `+ Новый актив`;
- поля `тикер`, `сумма`, `цена` должны быть сброшены;
- старая candidate-сделка не должна оставаться визуально или логически.

Пока нельзя считать закрытым:

- точный realized PnL по историческим продажам;

# Аудит схемы фактора здоровья v2

Дата: 2026-07-24

Статус: read-only audit. Код, Google Sheets, Apps Script, API contract и UI не менялись.

## 1. Вывод

Текущая модель фактора здоровья уже работает как risk-first модель, а не как
метрика прибыли. Шесть лучей соответствуют принятой логике:

1. Резерв;
2. Диверсификация;
3. Концентрация;
4. Контроль риска;
5. Выживаемость;
6. Дисциплина.

Главный риск сейчас не в формуле, а в контракте данных вокруг неё:

1. часть технических ключей осталась legacy и не совпадает с русскими названиями лучей;
2. план лимитных ордеров для выживаемости ещё не подключён как живой источник;
3. дисциплина считается из локального журнала, а не из общего источника фактов;
4. маржа GOLD под контролем плеча, но не включена в лимит 10% активной торговли;
5. схема входов `HealthInput` уже разрослась и требует явного v2-контракта.

## 2. Что уже реализовано правильно

### 2.1. Резерв

Источник: `src/lib/portfolioHealth.ts`, `src/config/riskRules.ts`.

Правила:

1. пол резерва — 10%;
2. цель резерва — 30%;
3. нормальный коридор — 30–60%;
4. ниже 10% включается жёсткая блокировка;
5. выше 60% появляется предупреждение о простаивающем капитале.

Оценка: логика соответствует манифесту. Резерв не трактуется как «чем больше,
тем лучше», это правильно.

### 2.2. Диверсификация

Источник: `computeDiversificationScore`, `DIVERSIFIABLE_CLASSES`.

Учитываются только спотовые рисковые классы:

1. Крипта;
2. Металлы;
3. Акции.

Кэш и фьючерсы исключены. Это правильно: резерв не должен портить
диверсификацию, а фьючерсы являются активным риском, а не классом долгосрочного
размещения.

Оценка: формула исправлена под стратегию 40/10/10 для рискового спота и уже
умеет давать 100 баллов при допустимой структуре.

### 2.3. Концентрация

Источник: `assetConcentration`, `preTradeGate`.

Уже есть:

1. ETH — 35% крипто-блока;
2. BTC — 20% крипто-блока;
3. SOL / TON / BNB — 10% крипто-блока;
4. прочие крипто-активы — 5% крипто-блока;
5. максимум 3 альткоин-места;
6. акции — 5% портфеля на актив, максимум 2 места;
7. металлы — 5% портфеля на актив, максимум 2 места.

Оценка: логика соответствует последним решениям. Важно сохранить единый
источник лимитов между `preTradeGate` и фактором здоровья.

### 2.4. Контроль риска

Источник: `computePortfolioHealth`, фьючерсный блок.

Уже есть:

1. лимит активной торговли — 10% капитала;
2. свободная часть лимита не штрафует здоровье;
3. превышение лимита даёт блокировку;
4. плечо по BTC/GOLD/XAU — до 3x;
5. плечо по прочим активам — до 2x;
6. максимум 3 активные позиции;
7. близость к ликвидации снижает балл.

Оценка: ключевой принцип «10% — максимум, не цель» реализован правильно.

### 2.5. Выживаемость

Источник: `src/lib/survivalEngine.ts`.

Уже есть стресс-сценарии:

1. крах крипты;
2. падение акций США;
3. обвал золота и металлов;
4. общий рыночный шок.

Движок считает:

1. худшую просадку;
2. портфель после шока;
3. резерв после шока;
4. покупательскую способность после шока;
5. влияние плана лимитных ордеров.

Оценка: луч не дублирует резерв. Он отвечает на вопрос: «система продолжит
работать после удара или нет».

### 2.6. Дисциплина

Источник: `behaviorEngine`, `decisionJournal`, `computePortfolioHealth`.

Уже есть:

1. покрытие журнала решений;
2. страх упустить рост;
3. сделки после убытка;
4. переторговка;
5. повторные блокировки;
6. дисциплинарная пауза;
7. влияние дисциплины на фактор здоровья.

Оценка: дисциплина перестала быть текстом в манифесте и уже влияет на Health
Factor.

## 4. Чего не хватает для полноценной схемы v2

### 4.1. Явные русские ключи лучей

Сейчас в коде есть legacy-ключи:

1. `crypto` фактически означает «Выживаемость»;
2. `futures` фактически означает «Контроль риска»;
3. `flexibility` фактически означает «Дисциплина».

Риск: будущие изменения легко начнут читать ключ буквально и сломают смысл.

Нужна схема:

1. `reserve`;
2. `diversification`;
3. `concentration`;
4. `riskControl`;
5. `survival`;
6. `discipline`.

Переименование нужно делать отдельным patch, потому что эти ключи используются
в UI, рекомендациях, тестах и симуляторе.

### 4.2. Источник плана лимитных ордеров

Поле `plannedLimitOrdersUsd` уже поддерживается формулой, но в живой сборке
данных оно не заполняется.

Сейчас результат честный: выживаемость предупреждает, что план лимитных ордеров
не подключён.

Нужно:

1. определить источник в Google Sheets;
2. читать сумму плановых лимитных ордеров через API;
3. передавать в `healthInput`;
4. показывать в выживаемости не «источник не подключён», а реальный план.

### 4.3. Общий источник журнала решений

Сейчас журнал решений работает в продукте, но хранится локально на устройстве.
Это хорошо для быстрого MVP, но плохо для долгосрочной операционной системы.

Нужно:

1. вынести журнал решений в источник фактов;
2. синхронизировать между устройствами;
3. дать отчётам историю дисциплины;
4. передавать дисциплинарную паузу не только во фронт, но и в автоматизации.

Важно: это требует проектирования структуры данных и не должно делаться
случайным patch.

### 4.4. Маржа GOLD в лимите активной торговли

Сейчас GOLD контролируется по плечу, если есть данные Hyperliquid, но сумма
маржи GOLD не включена в лимит 10% активной торговли.

В коде это прямо отмечено как временное ограничение.

Нужно:

1. получить точную маржу GOLD;
2. включить её в `futuresUsedUsd`;
3. не смешивать металл как класс портфеля и плечевой риск как риск торговли;
4. обновить тесты контроля риска.

### 4.5. Карманы капитала внутри HealthInput

Сейчас `capitalBuckets` есть для проверки сделки, но не является явной частью
схемы здоровья.

Нужно решить, должны ли в фактор здоровья входить:

1. заблокированный резерв;
2. рабочий капитал;
3. карман ручной крипты;
4. карман усреднения;
5. карман фьючерсов;
6. карман металлов;
7. карман акций.

Предварительный вывод: карманы не должны становиться отдельными лучами, но
должны быть метаданными для резерва, выживаемости и проверки сделки.

## 5. Предложение схемы фактора здоровья v2

```ts
type HealthFactorV2Input = {
  portfolio: {
    totalValueUsd: number;
    investedUsd: number;
    reserveUsd: number;
    reserveShare: number;
  };

  allocation: {
    cryptoShare: number;
    metalsShare: number;
    stocksShare: number;
    futuresShare: number;
    cashShare: number;
    riskSpotShares: [number, number, number];
  };

  capitalBuckets?: {
    lockedReserveUsd: number;
    workCashUsd: number;
    cryptoSpotBudgetUsd: number;
    averagingBudgetUsd: number;
    futuresBudgetUsd: number;
    metalsBudgetUsd: number;
    stocksBudgetUsd: number;
  };

  concentration: {
    score: number;
    worstAsset: string;
    worstShare: number;
    worstLimit: number;
    maxUtilization: number;
    overLimitAssets: string[];
    altcoinSlots: { used: number; total: number };
    stockSlots: { used: number; total: number };
    metalSlots: { used: number; total: number };
  };

  activeRisk: {
    usedShare: number;
    usedUsd: number;
    capUsd: number;
    legs: Array<{
      asset: string;
      marginUsd?: number;
      leverage: number | null;
      liquidationDistance: number | null;
    }>;
  };

  survival: {
    plannedLimitOrdersUsd?: number;
    spotDeployableUsd?: number;
  };

  discipline: {
    journalCoverage?: number;
    violations30d?: number;
    fomoEvents30d?: number;
    revengeTrades30d?: number;
    overtradingDays30d?: number;
    cooldownActive?: boolean;
  };
};
```

## 7. Что делать следующим code patch

Рекомендуемый следующий patch должен быть маленьким:

1. не менять формулы;
2. не менять UI;
3. не менять API;
4. добавить слой совместимости ключей:
   `crypto → survival`, `futures → riskControl`, `flexibility → discipline`;
5. обновить тесты, чтобы результат явно содержал канонические ключи v2;
6. после этого отдельно перевести UI и рекомендации на новые ключи.

Так мы не сломаем текущий гексагон, но уберём главный технический риск:
расхождение между смыслом луча и его внутренним именем.

## 3. Критические ошибки

### P0. Apps Script жены содержит публичные write-действия

Статус: исправлено и развернуто в Apps Script v18. Публичный `doGet` работает как read-only JSON.

Файл: `WIFE_APPS_SCRIPT.js:33-76`.

До исправления публичный `doGet` принимал действия:

- `?action=fixUsdt`;
- `?action=fixUsdtNow`;
- `?action=syncKoshaPriceSheet`.

Проблема: после удаления `shared secret` эти действия потенциально доступны напрямую по публичному URL веб-приложения. Это уже не read-only API. Любой, кто знает URL, может попробовать запустить запись в таблицу.

Что сделано:

- оставить публичным только чтение JSON;
- write-действия удалить из публичного `doGet` или закрыть отдельной проверкой токена;
- `syncKoshaPriceSheet` запускать вручную из Apps Script или через защищенный endpoint.

### P1. API неверно определяет крупнейший риск

Статус: исправлено и развернуто в Apps Script v18. `largestRiskAsset` теперь считается по максимальной доле позиции.

Файл: `WIFE_APPS_SCRIPT.js:206-215`, `WIFE_APPS_SCRIPT.js:254-260`.

До исправления API брал `best` позицию по PnL и использовал ее как `largestRiskAsset`.

До исправления API возвращал:

- `largestRiskAsset: GOLD`;
- `largestRiskShare: 1.77`.

После исправления API возвращает:

- `ETH`;
- около `77.17%` портфеля.

Влияние: API-риск и health API считаются по неверной концентрации. Сайт частично маскирует это своей пересборкой данных, но сам источник API неправильный.

Что сделано:

- считать `largestRiskAsset` по максимальной `share`, а не по лучшему PnL;
- в `computeHealth` передавать реальную крупнейшую долю.

### P1. В историю транзакций попадает строка заголовков

Статус: исправлено и развернуто в Apps Script v18. Заголовки и пустые строки больше не попадают в JSON как сделки.

Файл: `WIFE_APPS_SCRIPT.js:331-375`.

API возвращает одну транзакцию:

- `id: "ID"`;
- `asset: "Актив"`;
- `status: "Статус"`;
- `date: "Дата"`.

Это не транзакция, а русская строка заголовков из таблицы.

Влияние:

- отчеты и журнал могут показывать мусорную запись;
- любые будущие расчеты по истории будут загрязнены.

Что сделано:

- пропускать строки, где `id === "ID"` или `asset === "Актив"`;
- дополнительно пропускать строки без реальной даты, актива и действия.

### P1. Таблица `прайс / коша` не совпадает с API и сайтом

Статус: больше не является источником сайта. Таблица `прайс / коша` остается ручной бухгалтерией жены; сайт берет данные из отдельной таблицы `Жена`.

Проблема: таблица выглядит как источник контроля, но ее итоги устарели относительно API и сайта.

Что не трогать сейчас:

- не привязывать сайт к `прайс / коша`;
- не считать эту вкладку источником портфельных данных;

### P1. Рекомендации противоречат risk-first логике

Статус: исправлено локально в `src/v2/lib/healthCoreHelpers.ts`. При жестком дефиците резерва активные рекомендации на расширение портфеля скрываются.

Файл: `src/v2/lib/healthCoreHelpers.ts:459-539`.

На сайте одновременно показываются:

- `Не открывать новые позиции: резерв ниже пола 10%`;
- `Пополнить торговый баланс — покупательская сила на нуле`;
- `Добавить ≈$1,472 в металлы / акции`.

Проблема: при резерве `5.66%` и торговом капитале `$0` система не должна рекомендовать добавлять новые классы как активное действие. Сначала восстановление резерва, потом покупки.

Что сделано:

- если `reserveBlockers.length > 0` или `deployableCapital < 50`, рекомендации на покупку/добавление классов переводить в режим "после восстановления резерва";
- на главном экране оставлять только действия, которые реально можно выполнять сейчас.

## 7. Security / Privacy

### P0. Публичный Apps Script URL нельзя оставлять с write-actions

Даже если сайт ходит через защищенный `/api/investor-wife`, прямой URL Apps Script остается доступен отдельно.

Минимальная безопасная модель:

- public web app: только read-only JSON;
- mutation actions: только через private secret или ручной запуск из Apps Script;
- proxy whitelist: только нужные actions и только после Supabase auth.

### P2. Таблица `прайс / коша` публично читается через CSV

CSV экспорт доступен без авторизации. Если это сделано сознательно — ок. Если нет, это раскрывает состав и суммы портфеля.

## 10. Канонический Health

Решение: каноническим итоговым Health считается интерфейсная 6-лучевая модель.

Сейчас:

- API risk health показывает `10` и остается техническим риск-срезом Apps Script;
- UI Health показывает около `33/100`, потому что фронт собирает 6-лучевую модель через общий `computePortfolioHealth`;
- эта же модель используется в v2-слое и логике проверки решений.

Что не менять:

- не считать `risk.health` главным показателем здоровья;
- не подменять интерфейсный Health значением из API;
- не менять формулы 6 лучей отдельно для аккаунта жены.

Следующий аккуратный шаг: переименовать/отделить `risk.health` в API как вспомогательный риск-срез, чтобы он не конкурировал с основным Health в интерфейсе.

# 2. Что не входит в этот roadmap

Из плана убраны:

- закрытие публичного Apps Script `/exec`;
- shared-secret guard;
- smoke-token guard;
- дополнительная авторизация внутри Apps Script;
- усложнение доступа к Apps Script ради security;
- любые security-hardening задачи без отдельной модели угроз.

Текущее решение:

Apps Script остаётся простым публичным upstream-адаптером данных. Рабочая граница системы сейчас важнее дополнительных защит, которые уже ломали live-доступ.

# 3. Зафиксированная архитектура

Основная цепочка данных:

```text
Google Sheets
-> Apps Script API
-> Vercel API proxy
-> React / Vite frontend
-> Investor Cabinet UI
```

Правила:

- Google Sheets — источник фактов.
- Apps Script — читает/готовит данные из таблиц.
- Vercel API proxy — стабильная серверная граница для сайта.
- Frontend — отображает, нормализует и считает производные risk/health слои.
- Портфельные данные не хардкодим во frontend.
- Формулы и структуру таблиц не меняем без отдельной проверки зависимостей.
- API naming и JSON contract не меняем без отдельного contract patch.

# 5. P0 — стабильность live-данных

Цель:

чтобы сайт не проваливался в кэш или устаревшие данные при временных сбоях Apps Script / Vercel.

Уже сделано:

Что фиксить дальше только при повторении проблемы:

1. Добавить явный UI-текст, что `КЭШ` — это временное состояние до завершения live refresh.

3. Проверить таймаут wife endpoint, если прямой Apps Script снова отвечает дольше 35-70 секунд.
4. Сделать отдельный технический отчёт по задержкам Apps Script без изменения security-модели.

Проверка:

- `/api/investor` возвращает `200 JSON`;
- `/api/investor-wife` возвращает `200 JSON`;
- production UI переходит в `ЖИВЫЕ`;
- local UI переходит в `ЖИВЫЕ`;
- hard refresh не оставляет старые цифры;
- main и wife не смешиваются.

# 7. P1 — единый смысл Health

Цель:

убрать путаницу, когда разные слои показывают разные значения здоровья портфеля.

Текущая проблема:

- API может отдавать legacy health;
- frontend считает V2 Health;
- пользователь видит итоговое здоровье в UI и должен понимать именно его.

Решение на текущий этап:

V2 frontend Health считается главным отображаемым Health Score. Google Sheets / API дают исходные данные и legacy-поля, пока контракт не будет выровнен.

Патч:

1. Явно подписать в документации: V2 Health — отображаемый итог.
2. Legacy `overview.health` и `risk.health` не использовать как главный пользовательский итог.
3. Проверить все места UI, где показывается health.
4. Исправить копирайт, если один и тот же термин означает разные метрики.
5. Добавить тесты вокруг `computePortfolioHealth`.

Проверка:

- Overview, Health и Risk не конфликтуют по смыслу;
- нет ситуации, где `0`, `78`, `90` выглядят как один и тот же показатель;
- рекомендации соответствуют risk-first логике.

# 8. P1 — бухгалтерия и источник правды

Цель:

сохранить корректную логику учёта и не дать frontend стать вторым бухгалтерским движком.

Правила учёта:

- BUY увеличивает quantity и cost basis.
- SELL уменьшает quantity и cost basis по старой средней входа.
- SELL не пересчитывает avgEntry через proceeds.
- realized PnL считается отдельно.
- TRANSFER / IMPORT не меняют cost basis.
- SWAP раскладывается как SELL одного актива и BUY другого.

Патч:

1. Сверить main позиции с Google Sheets.
2. Сверить wife позиции с Google Sheets.
3. Проверить открытые позиции, закрытые позиции и stable rows.
4. Отдельно проверить futures.
5. Отдельно проверить резерв.
6. Не исправлять бухгалтерию во frontend.
7. Все расхождения фиксировать через Sheets / Apps Script слой.

Проверка:

- portfolioValue совпадает с таблицей;
- invested совпадает с таблицей;
- reserve совпадает с таблицей;
- positionsCount совпадает с таблицей;
- realized PnL не смешан с unrealized PnL;
- продажи не считаются покупками.

# 9. P1 — risk gate всегда главнее сигнала

Цель:

чтобы сайт никогда не подталкивал к покупке, если риск-слой запрещает действие.

Проблема:

сигналы, сценарии, DCA и рекомендации могут звучать как разрешение покупать, хотя лимиты или риск уже блокируют действие.

Правило продукта:

risk gate выше:

- buy signal;
- DCA ladder;
- scenario text;
- decision text;
- recommendation text;
- CTA.

Патч:

1. Проверить TON / MNT / futures / crypto share cases.
2. Если актив выше лимита — первым показывать блок риска.
3. Если резерв ниже нормы — первым показывать блок резерва.
4. Если futures близко к лимиту — показывать caution, не зелёный OK.
5. DCA и signal оставлять вторичным слоем.

Проверка:

- нет CTA на покупку выше лимита;
- рекомендации начинаются с ограничения, если оно есть;
- Signals и Risk не спорят друг с другом;
- pre-trade gate блокирует действие понятнее, чем signal его предлагает.

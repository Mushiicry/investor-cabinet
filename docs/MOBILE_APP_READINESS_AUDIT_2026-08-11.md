# Кабинет инвестора — актуальный аудит пути к мобильному приложению

Дата среза: 2026-08-11  
Цель документа: сравнить исходные большие дорожные карты с текущим состоянием и зафиксировать следующий путь к рабочему мобильному приложению.
Граница документа: только аудит и дорожная карта. Без точечных исправлений кода, данных и продакшена.

---

## 1. Главный вывод

Мы заметно продвинулись относительно исходных дорожных карт.

Старые документы описывали продукт как:

```text
Рабочая премиальная MVP-версия
-> стабилизация и завершение ядра риска
-> стабилизированное ядро MVP
-> профессиональный дашборд и аналитика
-> движок решений
-> автоматизация и умные сигналы
-> серверная часть / SaaS-платформа
-> мобильное приложение
```

Текущая реальная стадия:

```text
Веб-MVP уже работает и используется
-> персональная операционная система инвестора уже живая
-> готовность к телефону стала ближайшим критическим этапом
-> устанавливаемое веб-приложение / нативное приложение нужно начинать только после заморозки API-контракта и мобильной проверки
```

То есть мобильное приложение больше не выглядит как дальний этап 9/10. Оно стало ближайшим продуктовым горизонтом, но правильная первая цель — не сразу iOS/Android, а надежный веб-продукт, которым удобно пользоваться с телефона.

Под "PWA" в этом документе имеется в виду устанавливаемое веб-приложение: сайт можно добавить на домашний экран телефона, открыть как отдельное приложение и показать последнее успешно загруженное состояние при проблемах с сетью.

```text
продакшен-сайт, нормально читаемый с телефона
-> устанавливаемое веб-приложение
-> нативная обертка только после стабилизации веб-ядра
```

Это значит: не нужно начинать мобильное приложение с нуля. Нужно стабилизировать и переупаковать текущее V2 веб-ядро.

Уже есть:

- `src/v2/styles/v2-mobile.css`

Но это пока адаптивный веб-интерфейс, а не приложение.

### 4.3 База живых данных

Уже есть:

- продакшен-эндпоинт `/api/investor`
- продакшен-эндпоинт `/api/investor-wife`
- Google Sheets как источник фактов
- Apps Script как внешний адаптер данных

- слой проверки API-контракта
- разделение аккаунтов

Для мобильного клиента это почти достаточная база, но ее нужно формально заморозить.

## 5. Что еще не готово для настоящего мобильного приложения

### P0. Заморозка API-контракта

Мобильное приложение нельзя строить на плавающем JSON.

Нужно зафиксировать:

- обязательные поля для `overview`;
- обязательные поля для `portfolio`;
- обязательные поля для `risk`;
- обязательные поля для `signals`;
- обязательные поля для `history`;
- обязательные поля для `transactions`;
- необязательные поля для `investorDNA`, `assetQuality`, `progress`;
- одинаковые правила для основного аккаунта и аккаунта Полины;
- поведение при пустых массивах и отсутствующих необязательных блоках.

Критерий готовности:

```text
мобильный клиент может отрисовать основной аккаунт и аккаунт Полины,
не зная внутреннюю структуру Google Sheets
```

### P0. Понятное отображение устаревших данных и кэша на телефоне

На телефоне статус данных должен быть очевиден.

Нужно, чтобы пользователь сразу видел:

- живые данные;
- обновляется;
- устарело;
- кэш;
- ошибка;
- время последней успешной загрузки;
- какой аккаунт открыт;
- можно ли доверять цифрам прямо сейчас.

Это критичнее, чем новая красивая анимация.

### P0. Проверка критических мобильных сценариев

Нужно проверить не “влезает ли сайт”, а выполняет ли телефонный сценарий:

1. Открыл приложение.
2. Понял состояние портфеля.
3. Увидел главный риск.
4. Понял, можно ли добавлять риск.
5. Увидел фьючерсный лимит, маржу и перебор/недобор.
6. Получил сигнал и понял, что делать.
7. Проверил сделку через страницу проверки.
8. Не потерялся в таблицах.

### P1. Слой устанавливаемого web-приложения отсутствует

Сейчас нет:

- `manifest.webmanifest`;
- service worker;
- предложение установить приложение;
- иконки приложения;
- режим открытия отдельным приложением;
- экран без сети / с ограниченным режимом;
- последнее успешно загруженное состояние с явной пометкой;
- понятное обновление версии приложения.

До нативной обертки лучше сделать PWA: устанавливаемую веб-версию приложения.

### P1. Слой push-уведомлений и глубоких ссылок отсутствует

Telegram-алерты есть, но мобильному приложению нужен другой слой:

- push-уведомления;
- глубокая ссылка в конкретный экран;
- настройки уведомлений;
- дедупликация;
- тихие часы / дисциплинарная пауза;
- понятное поведение, если API устарел.

## 7. Новая дорожная карта к рабочему мобильному приложению

### Спринт 0 — фиксация продакшен-базы

Цель: не начинать мобильное приложение поверх хвостов.

Статус: почти закрыто.

Что уже есть:

- `main` чистый;
- продакшен задеплоен;
- API основного аккаунта и Полины живой;
- счетчик позиций исправлен;
- GOLD/GOLD LONG дубль устранен;
- строки портфеля приведены ближе к текущей реальности.

Что еще проверить:

- один свежий мобильный скриншот после жесткой перезагрузки страницы;
- переключение основного аккаунта и Полины на продакшене;
- статус живых/устаревших/кэшированных данных на телефоне.

Критерий готовности:

- `git status` чистый;
- build/lint/test проходят;
- продакшен-сайт открывает свежую сборку;
- API основного аккаунта и Полины отвечают `success:true`.

### Спринт 1 — заморозка мобильного API-контракта

Цель: мобильный клиент получает стабильный контракт.

Действия:

1. Снять живой JSON основного аккаунта и Полины как эталонные примеры.
2. Обновить `docs/sheets/API_CONTRACT.md` или создать `docs/MOBILE_API_CONTRACT.md`.
3. Разделить поля на обязательные / необязательные / устаревшие.
4. Добавить контрактные тесты на ответ API основного аккаунта и Полины.
5. Зафиксировать fallback-правила для пустых массивов.
6. Зафиксировать допустимые значения статусов и категорий.

Критерий готовности:

- мобильный каркас может отрисоваться при пустых `signals`, `history`, `transactions`, `investorDNA`;
- основной аккаунт и Полина не смешиваются;
- состояние устаревших данных и кэша типизировано.

### Спринт 2 — аудит критических мобильных сценариев

Цель: доказать, что текущим веб-продуктом можно нормально пользоваться с телефона.

Проверить размеры экрана:

- 360 x 740;
- 390 x 844;
- 430 x 932;
- 768 x 1024.

Проверить экраны:

- Обзор;
- Портфель;
- модалка подробностей здоровья;
- Риск;
- Сигналы;
- Проверка сделки;
- Отчеты;
- Настройки / переключение аккаунта.

Критерий готовности:

- нет горизонтального переполнения;
- таблицы имеют мобильное представление;
- модалки открываются перед пользователем;
- нижняя навигация не перекрывает действия;
- гексагон здоровья читается;
- кнопки удобно нажимаются пальцем;
- длинный русский текст не ломает карточки.

### Спринт 3 — мобильный главный экран / карточка управления риском

Цель: первый экран на телефоне не должен быть уменьшенной копией десктопной версии.

Первый экран должен отвечать:

1. Данные живые или устарели?
2. Главный риск сейчас какой?
3. Можно ли добавлять риск?
4. Сколько свободной фьючерсной маржи?
5. Лимит фьючерсов, в позициях, свободно, добавить/убрать.
6. Одно главное действие сейчас.

Критерий готовности:

- пользователь за 10 секунд понимает состояние портфеля;
- нет необходимости листать весь десктопный дашборд;
- проверка риска важнее PnL и сигналов.

### Спринт 4 — оболочка устанавливаемого веб-приложения

Цель: получить поведение приложения без App Store.

Действия:

1. Добавить manifest-файл.
2. Добавить иконки.
3. Настроить открытие отдельным приложением.
4. Добавить service worker только для каркаса приложения, не для подмены живых финансовых данных.
5. Добавить экран без сети / с ограниченным режимом.
6. Зафиксировать последнее успешно загруженное состояние с явной пометкой "устарело".

Критерий готовности:

- можно установить на домашний экран телефона;
- открывается как приложение;
- без сети показывает последнее состояние и предупреждает, что данные не живые.

### Спринт 5 — push-уведомления и глубокие ссылки

Цель: превратить Telegram-алерты в мобильный цикл действия.

Действия:

1. Описать модель уведомлений.
2. Настроить дедупликацию.
3. Глубокая ссылка из алерта в "Сигналы" / "Проверку".
4. Тихие часы / дисциплинарная пауза.
5. Не отправлять сигнал как разрешение на сделку.

Критерий готовности:

- алерт ведет в проверку риска;
- пользователь видит допустимый размер действия;
- проверка риска может заблокировать сигнал.

### Спринт 6 — решение по нативной обертке

Только после спринтов 1-5.

Решение:

- если PWA достаточно — не делать нативную версию;
- если нужны push-уведомления, глубокие ссылки, биометрия или отдельный процесс релиза — рассмотреть Capacitor;
- React Native / Expo не начинать без отдельного решения, потому что это будет второй фронтенд.

## 8. Что не делать сейчас

Не делать сейчас:

- сразу Capacitor/iOS/Android;
- перенос на Supabase/Postgres;
- AI-ассистент;
- SaaS / многоаккаунтный режим;
- редизайн V2;
- новая палитра/геометрия;
- переписывание `V2Shell` или больших CSS-файлов целиком;
- превращать мобильную версию в отдельный продукт с другой логикой;
- хардкодить портфельные данные во фронтенде;
- менять названия API / структуру JSON без отдельного патча контракта.

## 9. Следующий конкретный шаг

Следующая правильная задача:

```text
Спринт готовности к мобильному приложению 1:
заморозить мобильный API-контракт для основного аккаунта и Полины
```

Минимальный результат:

1. `docs/MOBILE_API_CONTRACT_2026-08-11.md`
2. живые эталонные JSON-примеры основного аккаунта и Полины
3. таблица обязательных, необязательных и устаревших полей
4. тесты, что мобильный ответ API не падает на пустых необязательных блоках
5. явный контракт состояния живых, устаревших и кэшированных данных

После этого:

```text
Спринт готовности к мобильному приложению 2:
визуальная проверка 8 критических мобильных экранов
```

Только после этих двух спринтов стоит добавлять PWA-оболочку, то есть устанавливаемую веб-версию приложения.

## 10. Рабочая формула на следующий горизонт

```text
Пока не строить нативное приложение.
Сначала собрать надежный телефонный кабинет инвестора.
```

Порядок:

```text
заморозка контракта
-> проверка критических мобильных сценариев
-> главный экран, спроектированный сначала для телефона
-> устанавливаемая PWA-оболочка
-> push-уведомления и глубокие ссылки
-> нативная обертка, только если она все еще нужна
```

Главный критерий:

```text
С телефона пользователь должен быстро понять:
живые ли данные,
что с риском,
можно ли добавлять капитал/риск,
и какое одно действие сейчас безопасно.
```
